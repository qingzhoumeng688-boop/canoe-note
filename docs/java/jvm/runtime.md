# 03 运行时数据区

> 本篇导读：当一段字节码真正跑起来，它的变量、对象、方法调用都存放在哪里？JVM 把运行时内存划分成若干区域，有的线程共享、有的线程私有。本文逐一拆解程序计数器、虚拟机栈、堆、方法区/元空间、直接内存，重点讲清栈帧结构、对象的创建过程与内存布局。理解了这些区域，后面讲 GC 和 OOM 时才不会"对着空气调参"。

## 一、总览

JVM 在运行时会把内存划分为多个数据区。按"是否线程共享"可以一刀切开：

```text
                  运行时数据区 (Runtime Data Area)
   ┌──────────────────────────────────────────────────────┐
   │  线程共享 (所有线程都能访问同一份)                      │
   │  ┌────────────────────┐  ┌─────────────────────────┐  │
   │  │      堆 (Heap)      │  │   方法区 / 元空间         │  │
   │  │  new 出来的对象实例  │  │  类信息、常量、静态变量   │  │
   │  └────────────────────┘  └─────────────────────────┘  │
   │                                                        │
   │  线程私有 (每个线程独有一份, 随线程生灭)                 │
   │  ┌────────────┐ ┌────────────┐ ┌──────────────────┐   │
   │  │ 虚拟机栈    │ │ 本地方法栈  │ │   程序计数器       │   │
   │  │ 方法调用的  │ │ native 方法│ │  当前执行的位置    │   │
   │  │ 栈帧        │ │ 的栈帧      │ │                   │   │
   │  └────────────┘ └────────────┘ └──────────────────┘   │
   └──────────────────────────────────────────────────────┘
```

一句话：**堆和方法区是线程共享的，虚拟机栈、本地方法栈、程序计数器是线程私有的**。共享区域是 GC 的主战场，私有区域随线程创建而创建、随线程结束而销毁。

## 二、程序计数器

**程序计数器（Program Counter Register）** 是一块很小的内存，作用是**记录当前线程正在执行的字节码指令地址**——相当于一个"执行位置指针"。

为什么需要它？因为 CPU 在多线程下会轮转调度，一个线程被切走再切回来时，必须知道"我上次执行到哪一行了"，才能恢复现场继续跑。每个线程都有自己独立的程序计数器，互不影响。

它的两个特性值得记住：

- **唯一一个在《Java 虚拟机规范》中没有规定 `OutOfMemoryError` 的区域**——它的空间在编译期就能确定，不会扩容也不会溢出。
- 当线程正在执行 **`native` 本地方法**时，计数器的值为空（undefined），因为本地方法不是由 JVM 字节码引擎执行的。

## 三、虚拟机栈

**虚拟机栈（JVM Stack）** 是线程私有的，生命周期与线程相同。每**调用一个 Java 方法，就会创建一个"栈帧（Stack Frame）"并压栈；方法执行完（正常返回或抛异常）就出栈**。所有方法从 `main` 一路调用到底，本质上就是栈帧不断入栈出栈的过程。

一个栈帧内部又包含四部分：

```text
┌─────────────────────────────────────────────┐
│                栈帧 (Stack Frame)              │
├─────────────────────────────────────────────┤
│  局部变量表 (Local Variables)                  │
│    → 存放方法参数、局部变量；this 在索引 0      │
├─────────────────────────────────────────────┤
│  操作数栈 (Operand Stack)                      │
│    → 字节码指令在此压栈/出栈进行计算            │
├─────────────────────────────────────────────┤
│  动态链接 (Dynamic Linking)                    │
│    → 指向运行时常量池的方法引用，支持多态       │
├─────────────────────────────────────────────┤
│  方法返回地址 (Return Address)                 │
│    → 方法结束后回到调用者的位置                 │
└─────────────────────────────────────────────┘
```

## 四、栈的异常

虚拟机栈有两种截然不同的"撑爆"方式：

- **`StackOverflowError`**：栈的深度超过了虚拟机允许的范围。最常见原因是**递归没有正确的退出条件**，或者单个栈帧太大（比如方法里定义了超大的局部变量表）。它**不是** OOM，而是深度溢出。
- **`OutOfMemoryError: unable to create new native thread`**：当**线程数量太多**，操作系统无法再分配新的线程（受限于进程内存、ulimit）时抛出。注意这跟栈容量本身相反——有时**调小 `-Xss`** 反而能创建更多线程。

`-Xss` 用来设置每个线程栈的大小，默认在 Linux 上通常是 1MB 左右：

```bash
-Xss256k      # 把每个线程栈设为 256KB，能创建更多线程，但更易 StackOverflow
```

## 五、局部变量表

**局部变量表**存放方法的参数和局部变量，它有这些关键特性：

- **容量以"Slot（变量槽）"为单位**，一个 Slot 在 32 位下能存一个 `int`/`float`/`reference`/`returnAddress`，64 位的 `long`/`double` 占两个 Slot。
- **`this` 永远在索引 0**（实例方法才有，static 方法没有 `this`）。
- **局部变量表的大小在编译期就完全确定**，写进 `class` 文件的 `Code` 属性的 `max_locals` 里，运行时不再改变。
- **局部变量没有默认值！** 必须显式赋值后才能使用，否则编译不通过。这与"类变量（static）有零值、数组元素有零值"完全不同。

还有一个有趣的现象叫 **Slot 复用**：当某个局部变量超出其作用域后，它占用的 Slot 可以被后面的变量复用，从而节省空间。但这也可能导致一些诡异的 GC 行为（大对象本应被回收却因 Slot 仍持有引用而没回收），排查内存问题时要注意。

## 六、操作数栈

HotSpot 是**基于栈的执行引擎**（区别于基于寄存器的物理 CPU）。方法计算时，操作数在"操作数栈"上压入、弹出。以 `1 + 2` 为例，字节码执行过程如下：

```text
初始: 操作数栈 = [ ]
iconst_1      → 把常量 1 压栈:  [ 1 ]
iconst_2      → 把常量 2 压栈:  [ 1, 2 ]
iadd          → 弹出栈顶两个, 相加, 结果压栈:  [ 3 ]
istore_1      → 把 3 存到局部变量表槽位 1:  [ ]  (局部变量表[1]=3)
```

可以看到，加法不是直接拿寄存器算，而是"弹出两个、相加、再把结果压回去"。这套机制正是上一关字节码篇要逐条讲解的。这里先建立"栈式执行"的直觉：**所有运算都围绕操作数栈展开**。

## 七、堆

**堆（Heap）** 是 JVM 内存中最大的一块，也是**几乎所有对象实例和数组的存放地**。它是线程共享的，因此是**垃圾回收的主要战场**（所以 GC 也常被叫作"GC 堆"）。

逻辑上，堆按"分代"划分（这是基于"弱分代假说"的优化，详见 GC 篇），经典结构如下：

```text
┌───────────────────────────────────────────────────────┐
│                       堆 (Heap)                         │
│                                                         │
│  ┌──────────── 新生代 (Young) ────────────┐             │
│  │   Eden         S0 (From)     S1 (To)    │             │
│  │  (8)            (1)           (1)        │  ← 默认 8:1:1 │
│  └─────────────────────────────────────────┘             │
│                                                         │
│  ┌─────────────────────────────────────────┐            │
│  │              老年代 (Old)                  │            │
│  └─────────────────────────────────────────┘            │
└───────────────────────────────────────────────────────┘
```

新对象优先在 **Eden** 区分配；经历一次 Minor GC 后存活的对象被移入 **Survivor（S0/S1）**；在 Survivor 之间来回拷贝、年龄达到阈值后晋升到**老年代**。

需要特别说明：教科书说"对象都在堆上"，但现代 JVM 有**逃逸分析**优化——如果一个对象不会被外部线程/方法访问（未逃逸），JIT 可能做**栈上分配**或**标量替换**，直接在栈上分配甚至拆散成基本类型，从而减轻堆压力。所以"对象一定在堆上"在优化开启时并不绝对。

## 八、对象的创建过程

`new` 一个对象，在 JVM 内部要完整走一遍流程：

1. **类加载检查**：先看这个类是否已被加载、解析、初始化，没有则先走类加载。
2. **分配内存**：从堆里划出一块空间给新对象。分配方式取决于堆是否规整：
   - **指针碰撞（Bump the Pointer）**：堆规整时用，移动一个指针即可（Serial、ParNew 等带整理的收集器）。
   - **空闲列表（Free List）**：堆不规整时用，维护一张"哪些块空闲"的表（CMS 这类标记-清除收集器）。
3. **处理并发**：分配内存不是线程安全的，两种方案：
   - **CAS + 失败重试**：原子地挪指针。
   - **TLAB（Thread Local Allocation Buffer）**：每个线程在 Eden 预先分一小块私有缓冲，自己先在自己的 TLAB 里分配，**HotSpot 默认开启**（`-XX:+UseTLAB`）。
4. **零值初始化**：把对象字段设为默认值（0、false、null）。
5. **设置对象头（Object Header）**：写入 Mark Word、类型指针（指向类元信息）等。
6. **执行 `<init>`**：调用构造器，按程序给字段赋真正的值，对象才算"真正可用"。

## 九、对象的内存布局

在堆里，一个对象在 64 位 HotSpot 中的内存布局分为三块：

```text
┌─────────────────────────────────────────────────────┐
│  对象头 (Header)                                      │
│    ├─ Mark Word   (8 字节, 哈希码/锁状态/GC 年龄...)   │
│    ├─ 类型指针 Klass Pointer (开启压缩后 4 字节)        │
│    └─ 数组长度 (仅数组对象有, 4 字节)                   │
├─────────────────────────────────────────────────────┤
│  实例数据 (Instance Data)                             │
│    → 各字段的实际值, 受字段重排优化影响                │
├─────────────────────────────────────────────────────┤
│  对齐填充 (Padding)                                   │
│    → 保证整体是 8 字节的整数倍                        │
└─────────────────────────────────────────────────────┘
```

一个计算示例：一个**普通空对象**（无字段），在 64 位、开启压缩指针（`-XX:+UseCompressedOops`，默认开启）时：

- Mark Word：8 字节
- 类型指针：4 字节（压缩后）
- 实例数据：0 字节
- 对齐填充：补到 8 的倍数 → 12 向上对齐到 16 字节

所以一个空对象占 **16 字节**。这也解释了为什么"对象很轻"但有基础开销。如果关闭压缩指针（`-XX:-UseCompressedOops`），类型指针变 8 字节，空对象就会占 24 字节——**开启压缩指针能显著降低内存占用**，这也是默认开启的原因。

## 十、对象的访问定位

Java 程序通过栈上的 `reference` 来操作堆里的对象，但 `reference` 如何找到对象有两种主流方式：

```text
方式一: 句柄 (HotSpot 不用)
  栈 reference → 句柄池(含: 到对象实例指针 + 到类元数据指针) → 对象实例/类元数据
  优点: 对象移动(GC)只改句柄, reference 不变
  缺点: 多一次间接访问

方式二: 直接指针 (HotSpot 采用)
  栈 reference ─────────────────→ 对象实例(内含类型指针) → 类元数据
  优点: 访问快, 少一次跳转
  缺点: 对象移动时要改所有 reference
```

**HotSpot 采用直接指针**，因为它更快——少一次内存寻址。GC 时对象被移动（复制/整理）则去更新栈上的 `reference` 即可。

## 十一、方法区与元空间

**方法区（Method Area）** 是线程共享的，存放**已被加载的类信息、常量、静态变量、即时编译器编译后的代码缓存**等。它在不同 JDK 版本的"物理落点"发生过重大变化：

- **JDK 7 及以前：永久代（PermGen）**，是**堆的一部分**，大小固定且难以调优，极易因加载类过多而 `OutOfMemoryError: PermGen space`。
- **JDK 8 起：元空间（Metaspace）**，把方法区**移到了本地内存（Native Memory）**，不再占用堆。默认情况下**只受本机物理内存限制**（不会一上来就 OOM），但仍可配置上限。

为什么要迁移？三个原因：① 永久代大小难预估，设小了 OOM、设大了浪费；② 永久代 GC 效率低、回收条件苛刻；③ 统一 HotSpot 与 JRockit 的实现（JRockit 本就没有永久代）。

相关参数：

```bash
-XX:MetaspaceSize=256m          # 元空间初始阈值, 触发首次 GC 的水位线
-XX:MaxMetaspaceSize=512m       # 元空间最大上限, 防止无限占用本机内存
```

如果动态生成大量类（如大量 CGLib 动态代理、Groovy 脚本、反射生成类）且未受控，元空间仍会撑爆，报错为 `OutOfMemoryError: Metaspace`。

## 十二、字符串常量池的位置变化

`String` 的字符串常量池（String Table）位置也跟着版本变迁，是个经典的"坑"：

```text
JDK 6:  字符串常量池 在 永久代(PermGen) 里
JDK 7:  字符串常量池 被移到 堆(Heap) 里
JDK 8:  字符串常量池 仍在 堆 里; 元空间只存类的元信息(类里常量池的"引用")
```

这带来实际影响：JDK 7 之前 `intern()` 把字符串放进永久代，容易 OOM；JDK 7 之后放进堆，受堆大小限制、能被 GC 回收，更安全。理解这一点对排查 `String` 相关内存问题和理解 `intern()` 行为至关重要（详见 String 篇）。

## 十三、直接内存

**直接内存（Direct Memory）** 不属于 JVM 运行时数据区，而是**操作系统本地内存**，但通过 NIO 被 Java 频繁使用：

- `java.nio.DirectByteBuffer` 会在**堆外**分配一块内存，Java 堆里只保留一个"指向它的引用"。这样做 I/O（如网络/文件读写）时可以**避免堆内 Buffer 到内核态的二次拷贝**，提升性能。
- 直接内存**不受 `-Xmx` 堆大小限制**，但受本机总内存限制；如果堆设得很大、又把直接内存用满，就会触发 `OutOfMemoryError`。
- 可用 `-XX:MaxDirectMemorySize` 限制其上限。
- 底层其实是通过 `Unsafe.allocateMemory` 直接调用系统 `malloc` 分配的。

```java
package com.canoe.jvm.runtime;

import java.nio.ByteBuffer;

public class DirectMemoryDemo {
    public static void main(String[] args) {
        // 在堆外分配 1MB 直接内存, 堆内只持有一个引用
        ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024);
        buffer.put((byte) 1);
        // 注意: 直接内存的回收依赖 GC 触发的 Cleaner, 不是普通 GC 立即回收
    }
}
```

## 本篇小结

- **堆和方法区线程共享，虚拟机栈/本地方法栈/程序计数器线程私有**。
- **程序计数器是唯一的"无 OOM 区域"**，native 方法执行时其值为空。
- **每个方法调用对应一个栈帧**，含局部变量表、操作数栈、动态链接、返回地址。
- **`StackOverflowError` 是栈太深（递归），OOM 是线程太多**，二者成因不同。
- **局部变量表编译期定大小，`this` 在索引 0，且局部变量无默认值**。
- **HotSpot 是基于操作数栈的执行引擎**，`1+2` 走 iconst/iadd/istore。
- **堆按分代划分，Eden:S0:S1 默认 8:1:1**，是 GC 主战场。
- **对象创建六步**：类加载检查→分配内存→并发处理→零值→对象头→`<init>`。
- **64 位开启压缩指针时空对象占 16 字节**，压缩指针默认开启以省内存。
- **HotSpot 用直接指针访问对象**，元空间（JDK 8+）在本地内存、字符串常量池在堆。
- **直接内存堆外分配、不受 `-Xmx` 限制**，用 `MaxDirectMemorySize` 限制。
