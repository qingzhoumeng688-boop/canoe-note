# 01 线程基础

> 本篇导读：很多同学一上来就背 `synchronized`、背线程池，却说不清"线程到底是什么、为什么需要它"。本篇从进程与线程的区别、并发与并行的辨析、JVM 内存模型，一直讲到线程安全问题产生的根因。读完你会明白：共享内存既带来了通信的便利，也埋下了线程安全的地雷。

## 一、进程与线程

计算机干活时需要一个"执行单元"。最粗的粒度是**进程（Process）**，最细的粒度是**线程（Thread）**。

一个很形象的比喻：

- **进程**像一座工厂，它有独立的厂房（地址空间）、独立的供电供水（系统资源）。
- **线程**像工厂里的工人，多个工人共享同一座厂房，但各自在自己的工位上干活。

换句话说，进程是**资源分配的最小单位**，线程是 **CPU 调度的最小单位**。一个进程里可以跑多个线程，这些线程共享进程的内存空间。

它们的核心区别：

| 对比维度 | 进程 | 线程 |
| --- | --- | --- |
| 地址空间 | 各自独立，互不干扰 | 共享所属进程的内存 |
| 切换开销 | 大（要切页表、刷 TLB） | 小（只切寄存器与栈） |
| 通信方式 | 管道、消息队列、共享内存、Socket | 直接读写共享变量（更快，也更危险） |
| 健壮性 | 一个进程崩溃不影响别人 | 一个线程崩了，整个进程都可能挂掉 |
| 创建成本 | 高 | 低 |

这解释了为什么我们偏爱多线程：它比多进程更轻量、通信更便宜。代价是"共享内存"这一便利本身，正是后面所有线程安全问题的源头。

## 二、为什么要用多线程

**收益：**

- **充分利用多核**：现代 CPU 都是多核的，一个单线程程序哪怕再忙，也只能用一个核，其余核都在围观。开多线程才能把算力吃满。
- **提高响应性**：在 GUI 或服务端，把耗时操作丢到后台线程，主线程（比如界面、接收请求的线程）不被阻塞，用户才不会"卡死"。
- **提高吞吐**：服务端同时处理多个请求，总体 QPS 上去了。

**代价（别只看到好处）：**

- **上下文切换开销**：线程多了，CPU 在线程之间来回切，要保存/恢复寄存器、栈，切得太频繁反而拖慢整体速度。
- **线程安全问题**：共享变量如果不加保护，会出现数据错乱（见第七节）。
- **资源消耗**：每个线程都要占栈内存（默认 1MB 左右），线程开太多会撑爆内存。

一句话：**多线程是"用复杂度换性能"，不是免费的午餐。**

## 三、并发 vs 并行

这是面试高频题，但很多人讲不清楚。

- **并发（Concurrency）**：多个任务在**同一时间段内交替执行**。哪怕只有一个核，靠时间片轮转，宏观上看像是在"同时"进行。
- **并行（Parallelism）**：多个任务在**同一时刻真正同时执行**，必须有多核支撑。

```text
单核 CPU（并发，交替执行）：
线程A: ██░░██░░██░░          ← 时间片轮转，宏观上看像"同时"
线程B: ░░██░░██░░██

多核 CPU（并行，真正同时执行）：
  核心1: ████████  ← 线程A
  核心2: ████████  ← 线程B
```

**一句话总结**：并发是"**一个厨师颠勺时轮流照看两口锅**"（交替），并行是"**两个厨师各看一口锅**"（同时）。并发解决"有活儿要排队"的问题，并行解决"活儿太多不够快"的问题。

## 四、线程的组成

一个 Java 线程在 JVM 里由这些部分组成：

- **线程 ID**：唯一标识。
- **程序计数器（PC）**：记录当前执行到哪条指令，线程私有的"书签"。
- **虚拟机栈**：方法调用时压入栈帧，局部变量就存在这里。
- **状态**：新建、运行、阻塞等（详见"03 线程状态与生命周期"）。

它们和 JVM 内存区域的关系如下（重点看哪些是私有的、哪些是共享的）：

```text
                    JVM 进程内存
┌─────────────────────────────────────────┐
│  堆 Heap              ← 所有线程共享        │
│    对象实例、成员变量                         │
├─────────────────────────────────────────┤
│  方法区 Method Area    ← 所有线程共享        │
│    类信息、静态变量、常量池                   │
├──────────┬──────────┬────────────────────┤
│ 线程1私有 │ 线程2私有 │ 线程N私有            │
│ 程序计数器 │ 程序计数器 │ 程序计数器           │
│ 虚拟机栈   │ 虚拟机栈   │ 虚拟机栈            │
│ (局部变量) │ (局部变量) │ (局部变量)          │
└──────────┴──────────┴────────────────────┘
```

## 五、线程的调度

线程数往往多于 CPU 核数，怎么分配 CPU？靠**调度器**。

- **时间片轮转**：每个线程分一小段时间（毫秒级），用完就换下一个，大家轮流用 CPU。
- **抢占式调度**：高优先级线程可以抢到低优先级线程的 CPU（JVM 用的是这种）。
- **协作式调度**：线程主动让出 CPU（如 `yield()`），自己不放手别人抢不走——现代操作系统基本不用。

**关于 Java 优先级的一个大实话**：`Thread.setPriority(1~10)` 只是给操作系统"提个建议"，**最终听不听由 OS 决定**。在 Windows、Linux 上映射方式不同，甚至可能完全忽略。所以**不要用优先级来保证业务正确性**，它不可靠。

## 六、线程与 JVM 内存

把第四节的图落到代码上，结论非常清晰：

- **堆和方法区是共享的** → 成员变量、静态变量多线程都能看到 → 这才有了线程安全问题。
- **栈和程序计数器是私有的** → 局部变量每个线程各有一份 → **局部变量本身是线程安全的**。

看下面这个会翻车的例子：多个线程同时改一个**成员变量** `count`，结果经常小于期望的 10000。

```java
package com.canoe.thread.base;

import java.util.ArrayList;
import java.util.List;

public class MemberUnsafeDemo {

    // 成员变量（实例字段），被多个线程共享
    private int count = 0;

    public void increment() {
        // 看起来只有一行，实际拆成 "读-改-写" 三步，不是原子操作
        count++;
    }

    public int getCount() {
        return count;
    }

    public static void main(String[] args) throws InterruptedException {
        MemberUnsafeDemo demo = new MemberUnsafeDemo();

        // 启动 10 个线程，每个线程自增 1000 次
        List<Thread> threads = new ArrayList<Thread>();
        for (int i = 0; i < 10; i++) {
            Thread t = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    demo.increment();
                }
            });
            t.start();
            threads.add(t);
        }

        // 等所有线程跑完
        for (Thread t : threads) {
            t.join();
        }

        // 期望是 10000，实际经常少于 10000
        System.out.println("最终 count = " + demo.getCount());
    }
}
```

如果把 `count` 从"成员变量"改成 `increment()` 方法里的**局部变量**，就不存在竞争了——因为每个线程各用各的栈帧。

## 七、什么时候会有线程安全问题

线程安全出问题，必须**三个条件同时满足**：

1. **多线程环境**（单线程当然没事）；
2. **有共享变量**（各用各的局部变量不会冲突）；
3. **对共享变量做了非原子操作**（读-改-写、检查再执行等）。

只要**破坏其中任意一个条件**，问题就消失了。对应三类解法：

- **破坏"多线程"**：没法破坏，本来就是要并发。
- **破坏"共享"**：用局部变量、用 `ThreadLocal` 把变量变成线程私有。
- **破坏"非原子"**：用 `synchronized`、`Lock`、`AtomicInteger` 等把操作变成原子的（或让变量不可变）。

所以你看到的几乎所有并发工具，本质都是在"消除共享"或"保证原子"这两件事上做文章。

## 八、线程数怎么定

线程不是越多越好（回顾第二节的切换开销）。经验公式：

- **CPU 密集型**（一直在算，很少等 IO）：线程数 ≈ **CPU 核数**，顶多加 1 防止偶发页缺失。
- **IO 密集型**（大量时间在等数据库、网络）：线程数 ≈ **核数 × (1 + 等待时间 / 计算时间)**。

```text
假设 8 核机器，一个任务 90% 时间在等 IO、10% 在计算：
  线程数 ≈ 8 × (1 + 0.9 / 0.1) = 8 × 10 = 80
```

实践中直接用公式拍脑袋不靠谱，**压测说话**：用 `jstat`、Arthas 观察 CPU 利用率、线程等待时间，逐步调优。

## 本篇小结

- **进程**是资源分配的最小单位，**线程**是 CPU 调度的最小单位，线程共享进程内存。
- 多线程的核心收益是**吃满多核、提高响应性和吞吐**，代价是切换开销与线程安全。
- **并发**是单核上交替执行，**并行**是多核上真正同时执行，二者不要混为一谈。
- 线程由 **ID、程序计数器、虚拟机栈、状态** 组成，其中栈和计数器是私有的。
- JVM 中**堆和方法区共享**，**栈和程序计数器私有**，这决定了线程安全问题的存在。
- **局部变量线程安全**，因为它在各自的栈帧里，互不干扰。
- **成员变量 / 静态变量不安全**，因为被所有线程共享，且非原子操作会相互穿插。
- 线程安全三条件是**多线程 + 共享变量 + 非原子操作**，破坏任一即可解决。
- Java 的**线程优先级不可靠**，只是给 OS 的建议，不要用它保证业务正确。
- CPU 密集型线程数约等于**核数**，IO 密集型用 **核数 × (1 + 等待/计算)** 估算。
- 一切并发工具的本质，都是在**消除共享**或**保证原子**上做文章。
