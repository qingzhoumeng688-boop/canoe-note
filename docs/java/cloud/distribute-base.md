# 01 分布式基础概念

> 本篇导读：分布式不是"把代码部署到多台机器"这么简单，它带来的是一整套全新的问题集合——网络会断、时钟会偏、节点会挂。本文先把"什么是分布式"讲清楚，再对比单体与微服务的区别，点名分布式一定会遇到的那些坑，最后给出一条从单机到服务化的真实演进路径，帮你建立整体认知框架。

## 一、什么是分布式系统

最朴素的定义：**分布式系统是一组通过网络协作、对外表现为一个整体（或一套系统）的计算机集合**。

我们先看单体（Monolith）：所有模块——用户、订单、库存、支付——都跑在**一个进程、连一个数据库**里，方法调用就是内存里的函数调用，快且简单。

```text
      单体架构
 -------------------------
 |  用户  订单  库存  支付  |
 |       (一个 JVM)        |
 |         |               |
 |      一个 MySQL          |
 -------------------------

      分布式架构
  ┌────────┐  ┌────────┐
  │用户服务│  │订单服务│   (各自进程、各自机器)
  └───┬────┘  └───┬────┘
      │   RPC/HTTP │
  ┌───┴────┐  ┌───┴────┐
  │库存服务│  │支付服务│
  └───┬────┘  └───┬────┘
      └────┬──────┘
       多个数据库
```

演进的核心动因是：当单体撑不住时，我们把不同模块**拆开**，让它们跨进程、跨机器协作。一旦跨了网络，函数调用就变成了远程调用，所有"网络的不确定"都找上门来了。

## 二、为什么要分布式

拆分布式主要为了四件事：

1. **突破单机性能瓶颈**：一台机器的 CPU、内存、磁盘、带宽都有上限，垂直扩容（换更大的机器）贵且有天花板，水平扩容（加机器）才是可持续之路。
2. **提高可用性**：单台机器挂了全站宕机；多台机器部署，挂一台还有其他的顶着。
3. **提升团队协作与发布效率**：大厂里一个系统几百人开发，单体改一行要全量回归、全员等发布；拆成独立服务后，各团队各发各的，互不影响。
4. **模块复用与独立伸缩**：秒杀服务平时流量小、大促流量大，可以单独给它加机器，而不用把整个系统都扩容。

但**代价是真实的**，见下一节。

## 三、分布式的代价

分布式不是银弹，它引入了一堆单体时代不存在的麻烦：

- **网络不可靠**：这是一切痛苦的根源。请求会**超时**、会**丢包**、会发生**网络分区**（一部分节点连不上另一部分）。你永远无法假设"发出去就一定到"。
- **节点故障是常态**：硬盘会坏、进程会 OOM、机器会断电。任何依赖"某台机器一直活着"的设计都会翻车。
- **一致性难以保证**：数据散落在多处，想让它们时刻一致，要么付出性能代价，要么接受短暂不一致。
- **运维复杂**：几十上百个服务，部署、监控、扩缩容、链路追踪，都需要一整套基建。
- **调试困难**：一个请求穿越 10 个服务，想知道卡在哪，必须上分布式链路追踪，否则只能"盲猜"。
- **数据不一致**：跨库、跨服务的写操作，部分成功部分失败是常事，需要补偿与对账。

一句话结论，也是本文的基调：**不要为了分布式而分布式**。单体能解决的问题，就别急着拆；拆，是因为单体的代价已经大于分布式的代价。

## 四、集群、分布式、微服务的区别

这三个词常被混用，其实层次不同：

- **集群（Cluster）**：同一个服务的**多份拷贝**，目的是高可用和负载均衡。比如部署 3 个完全相同的订单服务实例，前面挂个 Nginx 轮询。它们干的是同一件事。
- **分布式（Distributed）**：**不同模块协作**完成一件事。下单要订单服务 + 库存服务 + 支付服务一起配合，每个模块各司其职、可能在不同机器上。
- **微服务（Microservices）**：一种**分布式的架构风格**，强调服务足够小、围绕业务能力构建、可以**独立部署**、去中心化治理。微服务一定是分布式的，但分布式不一定都是微服务（比如一个庞大的分布式批处理系统）。

```text
集群：   订单服务×3   (同一个服务的副本)
         ↑ 负载均衡 ↑

分布式： 订单服务 → 库存服务 → 支付服务  (不同模块协作)

微服务： 分布式 + 小 + 独立部署 + 独立数据库 + 围绕业务
```

## 五、CAP 初步与分布式的核心矛盾

上一章专门讲 CAP，这里先埋个伏笔。分布式系统最核心的矛盾来自**网络分区**：当订单服务和库存服务之间的网络断了，库存到底扣没扣？

- 想保证强一致（C），就得在拿不准时拒绝服务（失 A）；
- 想保证高可用（A），就得先返回"成功了"，但可能数据其实是错的（失 C）。

这个"一致性与可用性的两难"，贯穿了后面所有的分布式技术：分布式锁、分布式事务、分布式 ID、幂等、限流熔断……**本质上都是在和这个矛盾打交道**。

## 六、常见的分布式问题

后面每一章都会展开，这里先点名，让你心里有张地图：

- **分布式锁**：多个进程抢同一份资源（如抢最后一个库存）时，如何保证只有一个能拿到。
- **分布式事务**：下单要同时写订单库、扣库存库、加积分库，如何保证"全成功或全回滚"。
- **分布式 ID**：分库分表后自增主键会重复，如何生成全局唯一且趋势递增的 ID。
- **接口幂等性**：网络重试导致同一请求到达两次，如何做到效果只发生一次。
- **限流 / 熔断 / 降级**：保护系统不被流量冲垮、不被慢下游拖死。
- **服务发现**：服务实例 IP 会变，调用方怎么找到它们。
- **配置管理**：几百个服务的配置如何集中管理、动态刷新。
- **链路追踪**：一个请求穿过多个服务，如何还原完整调用链。
- **分布式 Session**：用户登录状态在多台机器间如何共享。

## 七、分布式系统的度量

衡量一个分布式系统好不好，看这几个核心指标：

- **可用性（Availability）**：几个 9 的含义：

  ```text
  99%     一年宕机约 87.6 小时
  99.9%   一年宕机约 8.76 小时
  99.99%  一年宕机约 52.6 分钟
  99.999% 一年宕机约 5.26 分钟  (五个九，金融级)
  ```

  每多一个 9，成本和架构复杂度指数级上升。

- **响应时间（RT）**：平均值是陷阱，**P99**（99% 的请求都比它快）比平均值重要得多。平均 RT 100ms 可能掩盖了"1% 的请求要 3 秒"的长尾问题。
- **吞吐（QPS / TPS）**：每秒查询数 / 每秒事务数。容量规划的基础。
- **并发量**：系统同时处理的请求数。
- **容量规划**：根据目标 QPS 和单机能力反推需要多少机器：`机器数 ≈ 总QPS / 单机QPS / 冗余系数(如0.7)`。

## 八、架构演进路线

一条几乎所有互联网公司都走过的真实路径：

```text
1. 单机              (应用 + DB 同一台机器)
2. 应用与数据库分离  (各用一台机器)
3. 应用集群 + 负载均衡 (多份应用，Nginx 分流)
4. 数据库读写分离    (主写从读)
5. 引入缓存          (Redis 抗读热点)
6. 垂直拆分          (按业务拆成多个应用)
7. 水平拆分/分库分表  (单表太大，按 user_id 取模分片)
8. 服务化/微服务      (订单、库存、用户各自独立部署)
```

每一步都是被"上一步的瓶颈"逼出来的，不是拍脑袋设计的。**不要一上来就微服务**，从单机到服务化是一条渐进的路。

## 本篇小结

- **分布式系统** 是一组通过网络协作、对外表现为整体的计算机集合。
- **单体** 所有模块在一个进程一个库，**分布式** 模块拆开跨进程跨机器协作。
- **分布式的四动因**：突破单机瓶颈、提高可用性、提升协作效率、独立伸缩。
- **网络不可靠** 是分布式一切痛苦的根源：超时、丢包、分区。
- **集群** 是同一服务的多副本，**分布式** 是不同模块协作，**微服务** 是分布式的风格之一。
- **CAP 两难** 是分布式所有技术的核心矛盾。
- **常见分布式问题** 包括锁、事务、ID、幂等、限流、服务发现、配置、追踪。
- **P99 比平均值** 更能反映系统真实体验，长尾不可忽视。
- **可用性每多一个 9** 成本和复杂度指数级上升。
- **架构演进** 是渐进的：单机 → 分离 → 集群 → 读写分离 → 缓存 → 拆分 → 服务化。
- **不要为了分布式而分布式**，单体能解决就别急着拆。
