# 02 CAP 与 BASE 理论

> 本篇导读：CAP 和 BASE 是理解分布式系统的两把钥匙。很多面试八股只背"三选二"，却说不清为什么不能三选二、什么时候该保一致性、什么时候该保可用性。本文从定义出发，用具体的反证和时序图把 CAP 讲透，再引出 PACELC 与 BASE，最后给出一张"什么业务用什么一致性"的实战选型表。

## 一、CAP 的定义

CAP 是 Consistency（一致性）、Availability（可用性）、Partition tolerance（分区容错性）三个单词的首字母。注意，这三者描述的都是**系统层面的属性**，而不是某一个接口的属性。

- **C 一致性（Consistency）**：所有节点在**同一时刻**看到的数据完全一致。这里指的是**线性一致（linearizability）**——一旦某个写操作成功返回，之后所有的读都必须读到这个新值，连"中间状态"都不允许看到。打个比方：你在 ATM 取了 100 块，柜员机立刻显示余额少了 100，你手机银行也必须立刻显示少了 100，不能出现"一边是旧值、一边是新值"的窗口。
- **A 可用性（Availability）**：每一个到达系统的请求都能得到**响应**（不论成功还是失败），但不保证返回的是最新数据。可用性不等于"一直返回成功"，而是"一定能拿到一个响应，不会一直挂着"。
- **P 分区容错性（Partition tolerance）**：当网络发生**分区**（部分节点之间无法通信）时，系统仍然能够继续对外提供服务。比如机房之间光缆被挖断，A 机房和 B 机房连不上，但两边的用户都还能用系统。

一句话记忆：**C 是"大家看到的一样"，A 是"每次都有人理你"，P 是"网络炸了也能跑"**。

## 二、为什么三者不可兼得

关键在于：**网络分区是会真实发生的**。一旦分区发生，你就必须在 C 和 A 之间二选一。我们用一个最小反证来说明。

假设有两个数据节点 N1、N2，平时互相同步，现在它们之间网络断了（发生分区）：

```text
           客户端
             |
       +-----+-----+
       |           |
      N1          N2
       \          /
        \        /
      (网络断了 = 分区发生)

时序：
1. 客户端向 N1 写入 v = 2，N1 本地写成功
2. 由于分区，N1 无法把 v=2 同步给 N2，N2 仍然是 v=1
3. 客户端去读 N2，问：v 是多少？
   - 若要保证 C（一致性）：N2 必须返回错误/拒绝这次读
     → 客户端没拿到响应，失去 A（可用性）
   - 若要保证 A（可用性）：N2 必须返回响应，只能回旧值 v=1
     → 客户端读到了旧数据，失去 C（一致性）

结论：分区发生时，C 与 A 只能保一个，无法同时拥有。
```

注意这里**并没有说 P 可以不要**。分区是客观存在的故障，你没法"选择不要 P"。所以真正的命题不是"三选二"，而是"既然 P 必然在，那 C 和 A 选谁"。

## 三、P 是必选项

这是一个极其常见的误解，必须单独澄清：**CAP 不是让你从三个里挑两个，而是在"P 必然发生"这个前提下，选 C 还是选 A。**

原因很朴素：只要是分布式系统，节点之间就一定靠网络通信，而网络一定会抖、会断、会丢包。你无法声明"我的系统永远不发生分区"，所以**分区容错性 P 是必选项，没得选**。你真正能设计的，是当分区真的来了：

- 宁可返回错误也不给旧数据（选 C，牺牲 A）—— 典型 CP 系统；
- 宁可给旧数据也要立刻响应（选 A，牺牲 C）—— 典型 AP 系统。

这也是为什么我们后面会说"CP 系统"和"AP 系统"，而不是"CA 系统"—— 因为 CA 在分布式世界里基本不存在（单机系统才是 CA）。

## 四、CP 与 AP 的代表

不同系统在不同场景下，对 C 和 A 的取舍不同：

- **CP 阵营（优先保一致性）**：
  - **Zookeeper**：ZAB 协议保证多数派写入，读强一致，但如果 Leader 选举期间整体不可用。
  - **etcd**：Raft 强一致，常用于 Kubernetes 的元数据存储。
  - **HBase**：依赖 HDFS 的强一致，写入需多数派确认。
  - **Redis 主从（某些模式）**：开启 `WAIT` 或 min-slaves 时偏向 CP（但默认异步复制其实是 AP 倾向）。
- **AP 阵营（优先保可用性）**：
  - **Eureka**：服务注册中心，设计上允许短暂数据不一致，甚至有"自我保护机制"宁可保留坏节点也不踢掉。
  - **Cassandra / DynamoDB**：最终一致，写入永远成功，靠后续修复达到一致。

要强调的是：**实际系统大多在两者之间做权衡，而不是非黑即白**。比如 Nacos 既能以 AP 模式运行（临时实例用心跳），也能切换到 CP 模式（持久实例用 Raft），具体看业务诉求。

## 五、PACELC

CAP 只讨论了"发生分区（P）时"该怎么选，但现实里**大部分时间网络是正常的，并没有分区**。那正常时候系统又该怎样？这就是 PACELC 要补的洞。

PACELC 的读法：**如果发生了分区（P），则在可用性和一致性之间选择（A 或 C）；否则（E，Else），在延迟（L）和一致性（C）之间选择。**

```text
            网络正常?
               |
      +--------+--------+
      |                 |
   是(Else)          否(Partition)
      |                 |
   L 还是 C ?       A 还是 C ?
   (延迟vs一致)     (可用vs一致)
```

核心洞见：**即便没有分区，你要强一致往往就要付出更高延迟的代价**（比如要等多数派确认）。所以"最终一致"在很多场景其实是为了换取更低的延迟。

## 六、BASE 理论

BASE 是对 CAP 中 AP 方向的理论延伸，它坦然接受"暂时不一致"，换取系统的高可用。三个字母：

- **Basically Available（基本可用）**：系统出现故障时，允许损失一部分可用性，但核心功能还在。例如大促时降级非核心页面、把"秒杀结果页"替换为"稍后查看"。
- **Soft state（软状态）**：允许系统中的数据存在中间状态，并且该状态不影响整体可用性。比如订单处于"支付中"这种过渡态。
- **Eventually consistent（最终一致）**：经过一个时间窗口后，所有副本的数据最终会达到一致。注意是"最终"，不是"实时"。

BASE 的精髓一句话：**我暂时给你旧数据，但我保证过一会儿一定会对上**。这对点赞数、浏览量、评论这类"晚几秒一致也没事"的场景非常合适。

## 七、强一致、弱一致、最终一致

这三者是"一致性强度"的连续光谱：

- **强一致（Strong Consistency）**：写操作完成后，立刻任何读都能读到新值。例如银行转账后余额、订单支付状态——这类数据必须强一致。
- **弱一致（Weak Consistency）**：系统不保证后续读能读到新值，甚至不保证什么时候能读到。例如某些缓存更新后的短暂窗口。
- **最终一致（Eventual Consistency）**：给一个时间窗口，窗口过后所有副本一致。例如朋友圈点赞数：你点完赞，自己手机立刻 +1（本地乐观），好友那边可能晚 1 秒才看到，但最终一定一致。

举两个例子判断该用哪种：

- **转账后的余额**：绝对要强一致。你转给别人 100，自己余额没扣，那是要出大事故的。
- **朋友圈点赞数**：最终一致就够了。晚一秒看到点赞数变化，没人会因此投诉。

## 八、一致性的实践选型

把业务按"不一致会不会出事"分类，直接给结论：

```text
业务类型                  推荐一致性        典型手段
------------------------  ---------------  ----------------------------
钱 / 账户余额 / 库存      强一致            分布式事务、数据库锁、行锁
订单状态 / 支付状态        强一致(或最终+对账) 状态机 + 对账补偿
注册 / 登录               视业务而定        唯一索引防重复
点赞数 / 浏览量 / 评论     最终一致          异步消息、缓存、定期聚合
好友关系 / 动态流          最终一致          写扩散/读扩散 + 补偿
配置 / 开关                最终一致          配置中心广播
```

一句话原则：**凡是"错了会直接丢钱或违法"的，上强一致；凡是"晚几秒无所谓的"，果断最终一致，把系统可用性拉满**。

## 九、分布式共识算法简介

当我们需要在多个节点之间就"哪个值是对的"达成一致（也就是选 C 时的底层支撑），就要靠共识算法。三个最常听到的：

- **Paxos**：Leslie Lamport 提出的理论基石，正确性有严格证明，但论文极其难懂，工程实现复杂。
- **Raft**：Paxos 的"可理解版本"，把共识拆成**领导选举（Leader Election）**、日志复制、安全性三部分。核心思想有两个：
  - **多数派（Quorum）**：只要超过半数（N/2+1）节点认可，就算达成一致，容忍少数派掉线。
  - **任期 / 选举（Term & Election）**：时间被切成若干个"任期"，每个任期最多一个 Leader；Leader 挂了就发起新任期选举。etcd、Consul 用的就是它。
- **ZAB**：Zookeeper 专用的原子广播协议，思想和 Raft 类似（也是 Leader + 多数派 + 任期），但为"主备数据同步"做了专门设计。

这些算法为后面的 Zookeeper、etcd、Nacos(CP 模式) 打下了"如何在分布式下达成强一致"的地基。记住两个关键词就够入门：**多数派**和**任期/选举**。

## 本篇小结

- **CAP 的 C** 指线性一致：写成功后所有读必须立即看到新值。
- **CAP 的 A** 指每个请求都有响应，但不保证是最新数据。
- **P 是必选项**：分布式系统无法避免网络分区，所以只能在 C 和 A 间取舍。
- **分区发生时**：保 C 就要拒绝读（失 A），保 A 就要返回旧值（失 C）。
- **CP 系统** 如 Zookeeper / etcd 优先保一致，牺牲部分可用性。
- **AP 系统** 如 Eureka / Cassandra 优先保可用，接受最终一致。
- **PACELC** 补充：无分区时要在延迟与一致性之间权衡。
- **BASE** 是 AP 的延伸：基本可用 + 软状态 + 最终一致。
- **强一致** 适用于钱、库存等出错即事故的场景。
- **最终一致** 适用于点赞、浏览量等可容忍延迟的业务。
- **共识算法** 靠"多数派 + 任期选举"在分布式下达成强一致。
- **Raft / ZAB** 用 Leader + 多数派确认，是 etcd 与 Zookeeper 的基石。
