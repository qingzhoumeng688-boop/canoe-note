# 01 设计模式概述与学习指南

> 设计模式不是语法糖，也不是某个框架，而是一套"被无数项目验证过的解耦套路"。本篇用打比方的方式讲清它是什么、为什么值得学，并给出 GoF 23 种模式总览、UML 类图基础，以及一条不绕弯路的学习路线。

## 一、设计模式是什么

先打三个比方，你就懂了：

- **建筑行业的标准户型**：开发商盖楼不会每栋都重新发明布局，而是复用经过验证的"三室一厅""南北通透"户型图。户型图就是造房子的"模式"。
- **围棋的定式**：高手遇到小目、星位等特定局面，落子顺序已经被反复验证为局部最优。新手照着"定式"下，通常不会崩盘。定式就是下棋的"模式"。
- **烹饪的配方**：同样的"红烧"手法，既能烧肉也能烧鱼。配方把"火候 + 顺序 + 配比"固化下来，别人照做就能复现味道。

把这套思路搬到面向对象编程里：**设计模式（Design Pattern）就是遇到"对象该怎么创建、类该怎么组合、对象间该怎么协作"这类反复出现的问题时，前辈总结出的"标准应手"。**

GoF（Gang of Four，四人组 Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides）在 1994 年的神作《Design Patterns: Elements of Reusable Object-Oriented Software》里给出了经典定义：

> 设计模式是对**被用来在特定场景下解决一般设计问题的类和相互通信的对象的描述**。

请务必记住三件"它不是什么"：

1. **它不是语法**——`interface`、`abstract` 是语法，模式是用语法搭出来的结构。
2. **它不是框架**——Spring 是框架，能直接拿来用；模式只是图纸，得你自己照着盖。
3. **它不是银弹**——它是"经验套路"，用错了反而添乱（见第七节误区）。

## 二、为什么学设计模式

从三个最实在的角度说：

**1. 面试必考。** 随便打开一份 Java 中高级岗位的面经，"手写一个线程安全的单例""Spring 用了哪些设计模式""策略模式和状态模式有什么区别"几乎年年出现。不懂模式，八股都背不利索。

**2. 读源码的钥匙。** 你以为读不懂 Spring、MyBatis、JDK 是因为代码难？其实是因为你不认识里面的"套路"：

- `BeanFactory.getBean()` 背后是**工厂模式**；
- `JdkDynamicAopProxy` 背后是**代理模式**；
- `ApplicationListener` 事件机制背后是**观察者模式**；
- `java.util.Iterator` 背后是**迭代器模式**。

认出模式，源码瞬间从"天书"变成"老朋友"。

**3. 写代码抗变更。** 需求永远在变。今天会员打 9 折，明天要加"超级会员打 8 折还送积分"。如果不用策略模式，你的 `if-else` 会膨胀到没人敢动。模式的核心价值，就是**让变化发生时，你只加代码、不删老代码**。

最后泼盆冷水：**不要为了用模式而用模式。** 一个只被调用一次的小工具类，硬套个工厂 + 策略 + 模板方法，那是过度设计，同事会想打你。模式是为"变化"服务的，没变化就别上模式。

## 三、GoF 23 种模式总览

23 种模式按"创建型 / 结构型 / 行为型"分三类。下面这张大表建议收藏，面试前扫一眼就知道每个模式是干嘛的。

| 模式（中文） | 英文名 | 分类 | 一句话用途 | 常见度 |
| --- | --- | --- | --- | --- |
| 单例 | Singleton | 创建型 | 全局只存在一个实例（如配置中心、连接池） | 高频 |
| 工厂方法 | Factory Method | 创建型 | 让子类决定创建哪一个具体对象 | 高频 |
| 抽象工厂 | Abstract Factory | 创建型 | 创建一族互相配套的对象（如一套 UI 风格） | 中频 |
| 建造者 | Builder | 创建型 | 分步骤、可链式地构造复杂对象（如 `StringBuilder`） | 中频 |
| 原型 | Prototype | 创建型 | 通过拷贝自身来创建新对象（如浅/深拷贝） | 低频 |
| 适配器 | Adapter | 结构型 | 把不兼容的接口"转接头"成能用（如读卡器） | 高频 |
| 装饰器 | Decorator | 结构型 | 在不改原类的前提下动态叠加职责（如 IO 流） | 高频 |
| 代理 | Proxy | 结构型 | 为对象找"替身"控制访问（如远程/权限/延迟加载） | 高频 |
| 桥接 | Bridge | 结构型 | 把抽象和实现拆成两条独立的继承轴 | 中频 |
| 组合 | Composite | 结构型 | 用树形结构统一处理"单个对象"和"对象集合" | 中频 |
| 外观 | Facade | 结构型 | 给一大坨子系统提供一个干净的统一入口 | 中频 |
| 享元 | Flyweight | 结构型 | 共享大量细粒度对象以省内存（如字符串常量池） | 低频 |
| 策略 | Strategy | 行为型 | 把算法封装起来，运行时可替换（消灭 if-else） | 高频 |
| 模板方法 | Template Method | 行为型 | 父类定骨架，子类填空（如 `HttpServlet.service`） | 高频 |
| 观察者 | Observer | 行为型 | 一个变了，多个自动收到通知（如事件监听） | 高频 |
| 责任链 | Chain of Responsibility | 行为型 | 请求在一条链上挨个过，谁处理谁截断 | 中频 |
| 命令 | Command | 行为型 | 把"请求"封装成对象，可排队/撤销/重做 | 中频 |
| 状态 | State | 行为型 | 对象状态变了，行为跟着变（如订单状态机） | 中频 |
| 迭代器 | Iterator | 行为型 | 不暴露内部结构地顺序遍历集合 | 中频 |
| 中介者 | Mediator | 行为型 | 用"调度员"代替对象间网状互相调用 | 低频 |
| 访问者 | Visitor | 行为型 | 不改类的前提下，给类族加新操作 | 低频 |
| 备忘录 | Memento | 行为型 | 保存并恢复对象的历史状态（如撤销） | 低频 |
| 解释器 | Interpreter | 行为型 | 定义一门小文法并解释执行（如正则、表达式） | 低频 |

**学习优先级（先啃高频，低频可后放）：**

- 第一梯队（必须张口就来）：单例、工厂方法、策略、模板方法、观察者、适配器、装饰器、代理。
- 第二梯队（读源码常见）：抽象工厂、建造者、组合、桥接、责任链、命令、状态、迭代器、外观。
- 第三梯队（特定场景才用）：原型、享元、中介者、访问者、备忘录、解释器。

## 四、三种分类怎么记

记不住 23 个名字？先记住"三句话"，就能给任何一个模式归类：

- **创建型 = 怎么 `new`**：解决"对象怎么被创建出来"的问题，目的是把 `new` 的细节藏起来。典型：单例（只 new 一次）、工厂（不在业务里直接 new）、建造者（复杂对象分步 new）。
- **结构型 = 怎么组合**：解决"类和对象怎么拼装成更大的结构"的问题。典型：装饰器（套娃式加功能）、适配器（接口转接）、代理（套个壳控制访问）、组合（树形结构）。
- **行为型 = 怎么协作**：解决"对象之间如何分工、通信、职责划分"的问题。典型：策略（选算法）、观察者（发通知）、责任链（接力处理）、模板方法（父类定流程）。

一句话口诀：**创建管"生"，结构管"拼"，行为管"处"（相处）。**

## 五、UML 基础（读懂类图）

看源码、看模式书，第一关就是能读懂 UML 类图。其实就两块：**方框**和**六种关系**。

### 1. 方框与可见性

一个类的方框分三层：类名、属性、方法。可见性符号：`+` 公开（public）、`-` 私有（private）、`#` 受保护（protected）、`~` 包内（package-private）。

```text
┌──────────────────────┐
│       UserService    │   ← 类名（抽象类用 斜体 或 《abstract》）
├──────────────────────┤
│ - username: String   │   ← 属性，- 表示 private
│ # retryCount: int    │   ← # 表示 protected
├──────────────────────┤
│ + login(): boolean   │   ← 方法，+ 表示 public
│ - sendSms(): void    │
└──────────────────────┘
```

### 2. 六种关系（最易混的是聚合 vs 组合）

下面用 ASCII 图 + 一句话 + Java 对照，把六种关系一次讲清。

**(1) 依赖 Dependency（虚线箭头）**——"我用一下你，但你不归我管。"

```text
 ┌──────────┐         ┌──────────┐
 │  Order   │ - - -▷  │  Logger  │
 └──────────┘         └──────────┘
   Logger 只出现在 Order 的方法参数/局部变量里
```

```java
package com.canoe.pattern.overview;

// 依赖：Order 只在方法内部"用到"Logger，并不长期持有它
public class Order {
    public void pay(Logger logger) {   // Logger 是方法参数 → 依赖
        logger.info("订单支付成功");
    }
}
```

**(2) 关联 Association（实线箭头）**——"我长期认识你，把你当成成员变量。"

```text
 ┌──────────┐         ┌──────────┐
 │  Teacher │──────▷  │  Student │
 └──────────┘         └──────────┘
   Teacher 持有 Student 的引用（成员变量）
```

```java
package com.canoe.pattern.overview;

public class Teacher {
    private Student student;   // 长期持有引用 → 关联
    public void teach() { student.study(); }
}
```

**(3) 聚合 Aggregation（空心菱形 + 实线）**——"整体由部分组成的**has-a**，但**部分能脱离整体独立活**。"

```text
 ┌──────────┐      ◇────┌──────────┐
 │  Team    │─────────  │  Member  │
 └──────────┘           └──────────┘
   Team 解散了，Member 依然是独立的个人，可以加入别的 Team
```

```java
package com.canoe.pattern.overview;

import java.util.ArrayList;
import java.util.List;

// 聚合：Member 是从外部传进来的，Team 没了 Member 照样存在
public class Team {
    private List<Member> members = new ArrayList<Member>();

    public void addMember(Member member) {   // member 由外部创建后传入
        members.add(member);
    }
}
```

**(4) 组合 Composition（实心菱形 + 实线）**——"整体**contains-a**部分，**整体死了部分也跟着死**，生命周期绑定。"

```text
 ┌──────────┐      ◆────┌──────────┐
 │  Human   │─────────  │  Heart   │
 └──────────┘           └──────────┘
   Human 没了，Heart 也失去意义（同生共死）
```

```java
package com.canoe.pattern.overview;

// 组合：Heart 在 Human 构造时由 Human 自己 new 出来，同生共死
public class Human {
    private Heart heart;

    public Human() {
        this.heart = new Heart();   // 内部创建 → 组合
    }
}

class Heart { }
```

**(5) 泛化 Generalization（实线空心三角）**——就是"继承"，子类是父类的一种。

```text
 ┌──────────┐    △
 │  Animal  │────
 └──────────┘    │
              ┌──┴─────┐
              │  Dog   │   Dog 继承 Animal
              └────────┘
```

```java
package com.canoe.pattern.overview;

public class Dog extends Animal {   // 泛化 = 继承
}
```

**(6) 实现 Realization（虚线空心三角）**——类实现接口。

```text
 ┌──────────┐    △
 │ Runnable │- - -
 └──────────┘    │
              ┌──┴─────┐
              │  Task  │   Task 实现 Runnable
              └────────┘
```

```java
package com.canoe.pattern.overview;

public class Task implements Runnable {   // 实现 = 虚线三角
    @Override
    public void run() { }
}
```

**聚合 vs 组合 一图定生死**：看"部分能不能脱离整体单独存在"。能 → 聚合（空心菱形，`Team`/`Member`）；不能 → 组合（实心菱形，`Human`/`Heart`）。记住这个判据，面试再也不慌。

## 六、学习路线与建议

按这个顺序学，坡度最缓、收益最快：

```text
第 1 步  单例（最简单，先建立"模式感"）
   ↓
第 2 步  工厂方法 + 抽象工厂（理解"怎么藏 new"）
   ↓
第 3 步  策略 + 模板方法（消灭 if-else、复用流程）
   ↓
第 4 步  观察者 + 责任链（对象如何协作通信）
   ↓
第 5 步  代理 + 装饰器 + 适配器（结构型三巨头，容易混，放一起对比学）
   ↓
第 6 步  桥接 + 组合 + 外观 + 建造者（补全结构型）
   ↓
第 7 步  命令 + 状态 + 迭代器（常用行为型）
   ↓
第 8 步  享元 / 中介者 / 访问者 / 备忘录 / 解释器（低频，按需补）
```

**三条硬建议：**

1. **先理解"意图"，再背"结构"。** 模式的本质是"为了解决什么问题"。问题没搞懂，背下类图也没用。
2. **边学边在源码里"找模式"。** 学完观察者，去翻 `ApplicationListener`；学完装饰器，去翻 `BufferedInputStream`。看见真实代码，理解才落地。
3. **动手写，别只看。** 每个模式自己手敲一遍，哪怕只是个玩具例子。手感比眼睛重要。

## 七、常见误区

- **误区一：模式万能论。** 以为套上模式代码就"高级"了。错——模式只为"变化"服务，没有变化点硬上模式，只会增加复杂度。
- **误区二：背代码而不是背意图。** 把单例的某段代码背下来，却说不清"为什么要用 volatile"。面试官一追问就露馅。
- **误区三：过度设计。** 一个类只被用一次，非得上"工厂 + 策略 + 模板"。KISS（Keep It Simple, Stupid）原则优先。
- **误区四：不看场景照搬。** 别处的好方案，换个上下文可能就是坏方案。模式要"因地制宜"。
- **误区五：把原则当教条。** 七大原则是方向，不是铁律。偶尔为性能或可读性牺牲一点原则，是合理的工程权衡。

## 本篇小结

- **设计模式是"经验套路"**，不是语法也不是框架，核心目的是解耦与抗变更。
- **GoF 23 种**按创建型(5)、结构型(7)、行为型(11)分为三大类。
- **创建型管"怎么 new"**，把对象创建细节隐藏起来。
- **结构型管"怎么拼"**，负责类与对象的组合。
- **行为型管"怎么协作"**，负责对象间的分工与通信。
- **UML 方框**分三层：类名、属性、方法，可见性用 `+ - # ~` 表示。
- **依赖**是"用一下"，**关联**是"长期持有引用"。
- **聚合(空心◇)**与**组合(实心◆)**的根本区别：部分能否脱离整体独立存在。
- **泛化=继承**，**实现=实现接口**，二者三角箭头一个实线一个虚线。
- **学习顺序**：单例→工厂→策略→模板方法→观察者→代理/装饰/适配。
- **不要为了用模式而用模式**，没有变化点就保持简单。
- **理解意图比背结构更重要**，并在 Spring/MyBatis/JDK 源码里"找模式"才真正掌握。
