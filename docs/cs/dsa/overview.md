# 01 数据结构与算法概述及复杂度分析

> 本篇导读：本篇建立"算法+数据结构=程序"的整体认知，重点吃透时间/空间复杂度的大 O 表示法、最好/最坏/平均情况，以及递归复杂度分析，是后面所有章节的工具基础。

## 一、为什么要学数据结构与算法

1976 年，瑞士计算机科学家 Niklaus Wirth 写了一本经典小书，书名直白到像一句口号：**Algorithms + Data Structures = Programs（算法 + 数据结构 = 程序）**。这句话在今天依然成立：无论你写的是后端服务、前端页面还是嵌入式固件，本质上都是在"用某种结构组织数据，再用某种步骤处理数据"。结构选错、步骤选错，程序立刻变慢变笨。

先看一个最直观的效率差异。假设我们要从一个**有序数组**里查找一个数：

- **线性查找**：从头到尾一个一个比，最坏要把 `n` 个元素全看一遍，复杂度 `O(n)`。
- **二分查找**：每次和中间元素比，砍掉一半，最坏只要 `log2(n)` 次，复杂度 `O(log n)`。

当 `n = 10亿` 时，线性查找最坏要查 10 亿次，二分查找最坏只要约 30 次（因为 2^30 ≈ 10.7 亿）。这就是"选对算法"带来的天壤之别——不是快几倍，而是快几千万倍。

再看排序。把 10 万个数字排序：

- 冒泡、简单插入这类 `O(n²)` 算法要做约 `10^10`（100 亿）次比较。
- 快排、归并这类 `O(n log n)` 算法只要约 `10^5 × 17 ≈ 170 万`次。

差了将近 600 倍。更残酷的是，随着数据量增大，这个倍数会指数级拉开——这正是"算法思维"值钱的地方：**它决定了你的程序能不能扛住真实规模的数据**。

除了性能，数据结构与算法还决定了代码是否"优雅可维护"。一个用对了哈希表的人，绝不会写出"为了查重每次都遍历全表"的丑代码。所以这一篇不是"面试八股"，而是每个写代码的人都应该内化的基本功。

## 二、数据结构是什么

**数据结构（Data Structure）** 是计算机存储、组织数据的方式。它研究两件事：**数据之间是什么关系（逻辑结构）**，以及**这些关系在内存里怎么摆（存储结构）**。

### 逻辑结构：数据"想"长什么样

逻辑结构是数据之间的抽象关系，与机器无关，分四大类：

| 逻辑结构 | 特点 | 例子 |
| --- | --- | --- |
| **集合** | 元素同属一个集合，彼此无关系 | 一个班的学生名单 |
| **线性结构** | 元素一对一，排成一条线 | 数组、链表、栈、队列 |
| **树形结构** | 元素一对多，分层 | 文件系统目录、族谱、二叉搜索树 |
| **图状结构** | 元素多对多，任意连接 | 地图路网、社交关系、依赖图 |

### 存储结构：数据"实际"怎么摆

存储结构是逻辑结构在内存/磁盘上的物理实现，常见四类：

- **顺序存储**：元素在内存里一块挨一块连续摆放，比如数组。好处是随机访问快（`O(1)`），坏处是插入删除要搬数据。
- **链式存储**：每个元素带着"指向下一个的地址"，元素在内存里可以散着放，比如链表。好处是插入删除方便，坏处是不能直接跳到任意位置。
- **索引存储**：额外建一张"索引表"来快速定位，比如数据库的索引、书的目录。
- **散列存储（哈希）**：用哈希函数把关键字直接算出一个存放位置，理想情况下查找 `O(1)`，比如 `HashMap`。

### 逻辑与存储的关系

关键认知：**同一逻辑结构可以有多种存储实现**。比如"线性表"这个逻辑结构，既可以用顺序存储（数组）实现，也可以用链式存储（链表）实现；"树"既可以用数组（堆常用）也可以指针（二叉搜索树常用）实现。选哪种存储，取决于你的操作以"访问"为主还是以"增删"为主。后面每章我们都会反复做这个选择。

## 三、算法是什么

**算法（Algorithm）** 是解决某一类问题的明确、有限的步骤描述。一个合格的算法必须满足 5 大特性：

| 特性 | 含义 |
| --- | --- |
| **有穷性** | 步骤必须在有限时间内结束，不能死循环 |
| **确定性** | 同一条指令、同一输入，结果唯一确定，不能含糊 |
| **可行性** | 每一步都能用基本操作实现，不能出现"画个圆再平方"这种做不到的指令 |
| **输入** | 可以有零个或多个输入 |
| **输出** | 必须有一个或多个输出，光算不算输出等于没用 |

注意"有穷性"是算法和"计算过程"的本质区别：操作系统理论上永远不退出，它是一个计算过程，不是算法。

那怎么才算一个**好算法**？除了满足上面 5 条，还要追求 4 个目标：

- **正确性**：能算出对的结果，边界情况也不出错。
- **可读性**：人能看懂，方便维护和协作。变量名 `i`、`tmp` 满天飞的代码不是好代码。
- **健壮性**：对非法输入（如空指针、负数、越界）能优雅处理，而不是崩给你看。
- **高效性**：时间和空间开销都小——这正是后面复杂度分析要量化的东西。

这 4 个目标里，正确性是底线，可读性和健壮性是工程基本要求，而高效性往往需要在具体场景里权衡（比如用空间换时间）。

## 四、时间复杂度

衡量算法快慢，最直观的想法是"数它跑了多久"。但这太依赖机器、编译器、输入规模，没法横向比较。于是我们改用**渐近复杂度**：看当问题规模 `n` 趋于无穷大时，算法基本操作次数的增长趋势。

**大 O 表示法（Big-O notation）** 描述的就是这个"增长趋势的上界"。它只关心两件事：

1. **最高阶项**：比如 `3n² + 100n + 50`，当 `n` 很大时 `n²` 主导一切，低阶项和常数都被"淹没"。
2. **忽略常数系数**：`O(2n)` 和 `O(n)` 都写成 `O(n)`，因为我们关心的是"量级"而非"快几倍"。

为什么只留最高阶？因为复杂度分析的使命是回答"规模变大时，谁会先崩"。常数再大，也只是把曲线整体平移，不改变它向上冲的斜率。比如 `O(n²)` 和 `O(n)` 在 `n=1000` 时差距已经是 1000 倍，常数 `2` 或 `50` 根本救不回来。

常见阶的直观含义与增长对比：

| 复杂度 | 名称 | 直观含义 | n=10 | n=100 | n=1000 |
| --- | --- | --- | --- | --- | --- |
| `O(1)` | 常数 | 和规模无关，一步到位 | 1 | 1 | 1 |
| `O(log n)` | 对数 | 每次砍一半，增长极慢 | ~3 | ~7 | ~10 |
| `O(n)` | 线性 | 和规模成正比 | 10 | 100 | 1000 |
| `O(n log n)` | 线性对数 | 每层 `n`、共 `log n` 层 | ~33 | ~664 | ~10000 |
| `O(n²)` | 平方 | 两层嵌套遍历 | 100 | 10000 | 1000000 |
| `O(2ⁿ)` | 指数 | 每加一个元素翻倍 | 1024 | 巨量 | 天文数字 |

从表里能直接读出结论：**`O(2ⁿ)` 是灾难，`O(n²)` 在小规模还行、大规模劝退，`O(n log n)` 是可接受的分治排序基准，`O(n)` 和 `O(log n)`、`O(1)` 才是我们向往的效率**。

再看一张"增长曲线对比"帮助建立直觉（纵轴是操作数，横轴是 `n`）：

```text
操作数
 ^
 |                         O(2^n)
 |                      *
 |                   *
 |                *        O(n^2)
 |             *      *
 |          *    *        O(n log n)
 |       *  * *              O(n)
 |    * *    *                 O(log n)
 |  *   *                       O(1)
 +-------------------------------------> n
   (示意：曲线越靠左上越优，指数级会迅速"起飞")
```

### 大 O 是怎么"推"出来的：动手算一次

光记住结论不够，得会自己化简。给定一个具体表达式，按三步走：

1. **展开成基本操作次数**：比如某段代码总共执行了 `3n² + 5n + 7` 次核心操作。
2. **砍掉低阶项**：当 `n` 很大，`n²` 把 `n` 和常数远远甩开，`5n + 7` 直接舍去。
3. **丢掉常数系数**：`3n²` 的系数 `3` 只影响曲线高低不影响斜率，写成 `O(n²)`。

所以 `3n² + 5n + 7` → `O(n²)`。同理 `2n + 100` → `O(n)`，`4` → `O(1)`，`n·log n + n` → `O(n log n)`。一定要养成"看到表达式先找最高阶"的反射。

日常代码里，复杂度几乎都由固定的"代码结构模式"决定，熟记这张映射表就能秒判：

| 代码结构 | 复杂度 | 直觉 |
| --- | --- | --- |
| 一条不随 `n` 变的语句 | `O(1)` | 一次搞定 |
| 单层 `for (i=0;i<n;i++)` | `O(n)` | 走 `n` 步 |
| 两层嵌套 `for×for` | `O(n²)` | `n×n` |
| 循环里 `i *= 2`（翻倍） | `O(log n)` | 几步到 `n` |
| 循环里 `i *= k`（k>1） | `O(log_k n)` | 同上，底不同 |
| 分治递归每半层做 `O(n)` | `O(n log n)` | 层 `log n` × 每层 `n` |
| 递归每步分两路且不剪枝 | `O(2ⁿ)` | 指数爆炸 |
| 三层及以上嵌套 `for` | `O(n³)` 等 | 阶数随层数涨 |

## 五、最好/最坏/平均情况

同一个算法，面对不同输入，表现可能天差地别。于是复杂度要分三种情景来谈：

- **最好情况（Best）**：最幸运的输入，比如查找时目标恰好在第一个位置，复杂度 `O(1)`。
- **最坏情况（Worst）**：最倒霉的输入，比如目标在最后一个或根本不存在，复杂度 `O(n)`。
- **平均情况（Average）**：所有可能输入下的期望开销，通常假设输入均匀分布。

以**插入排序**为例（外层 `i` 从 1 到 `n-1`，内层把 `a[i]` 往前插）：

- 最好情况：数组已经有序，每个元素都不用往后挪，内层几乎不执行，复杂度 `O(n)`。
- 最坏情况：数组完全逆序，每个元素都要挪到最前面，总比较次数约 `n²/2`，复杂度 `O(n²)`。
- 平均情况：每个元素平均挪一半，仍是 `O(n²)`。

再以**快速排序**为例（选一个 pivot 分两半）：

- 最好情况：每次 pivot 都刚好把数组均分，递归深度 `log n`、每层 `n`，复杂度 `O(n log n)`。
- 最坏情况：每次 pivot 都选到最大/最小（比如数组已序且总选第一个），退化成 `O(n²)`。
- 平均情况：在随机输入下期望 `O(n log n)`，所以快排实践中非常快。

工程上我们**最看重最坏情况和平均情况**，最好情况往往只是"锦上添花"、用来安慰自己。

顺带提一句**摊还分析（Amortized Analysis）**：有些操作偶尔很贵、但大多数很便宜，把"贵的一次"分摊到前面多次便宜操作上，平均每次就是便宜的——比如动态数组扩容，单次扩容 `O(n)` 但均摊到每次插入只有 `O(1)`。一句话：**摊还复杂度看的是"一连串操作的平均单价"，而不是单次峰值**。

把最常见的几个排序最好/最坏/平均一次性摆出来，能更直观地体会"输入分布"的影响：

| 算法 | 最好 | 最坏 | 平均 | 说明 |
| --- | --- | --- | --- | --- |
| **插入排序** | `O(n)` | `O(n²)` | `O(n²)` | 已序时几乎不搬 |
| **冒泡排序** | `O(n)` | `O(n²)` | `O(n²)` | 加提前退出才可能最好 `O(n)` |
| **快速排序** | `O(n log n)` | `O(n²)` | `O(n log n)` | 最坏在 pivot 总选极值 |
| **归并排序** | `O(n log n)` | `O(n log n)` | `O(n log n)` | 与输入无关，稳定 |
| **堆排序** | `O(n log n)` | `O(n log n)` | `O(n log n)` | 同样与输入无关 |

这张表有个重要启示：**归并和堆排序的最坏也是 `O(n log n)`**，而快排最坏会退化。所以追求"稳定可预期"时用归并/堆排，追求"平均极快且空间省"时用快排——这也是很多语言标准库排序（如 Java `Arrays.sort` 对基本类型用双轴快排）的取舍逻辑。

## 六、空间复杂度

时间之外，算法还要吃内存。**空间复杂度**衡量的是算法运行时**额外占用**的存储空间随 `n` 的增长趋势，同样用大 O 表示。

注意"额外"二字：如果一个算法只是读取输入数组本身，那 `n` 个输入的空间不算算法的锅，我们算的是**除了输入之外新开辟的空间**。

几个关键概念：

- **原地算法（in-place）**：空间复杂度是 `O(1)`，即只用了常数个临时变量，不随 `n` 增长。比如原地反转数组、堆排序。它不意味"一点额外空间都不用"，而是"额外空间不随规模放大"。
- **非原地**：比如归并排序要额外开一个同规模的辅助数组，空间 `O(n)`。
- **递归栈与空间**：递归函数每调用一层，系统就要在调用栈上压入一帧（存参数、局部变量、返回地址）。递归深度为 `d`，空间复杂度就是 `O(d)`。比如单向递归求 `1+2+...+n` 深度 `n`，空间 `O(n)`；而尾递归或迭代可降到 `O(1)`。

一个容易混淆的点：**时间换空间、空间换时间**是永恒的主题。哈希表用 `O(n)` 的额外空间换来 `O(1)` 的查找；而有些压缩算法则用更多时间换更小空间。选型时要在两头之间权衡。

## 七、复杂度计算实战

理论讲完，来真刀真枪手算几段代码。记住心法：**看循环层数、看每轮执行的次数、相乘或相加，最后只留最高阶**。

**例 1：单层循环 → `O(n)`**

```java
package com.canoe.dsa;

public class Example1 {
    // 单层循环，执行 n 次
    public static int sum(int[] a) {
        int total = 0;
        for (int i = 0; i < a.length; i++) {  // 执行 n 次
            total += a[i];
        }
        return total;
    }
}
```

循环体执行 `n` 次，每次 `O(1)`，总 `O(n)`。

**例 2：两层嵌套循环 → `O(n²)`**

```java
package com.canoe.dsa;

public class Example2 {
    // 两层嵌套，i 和 j 各跑 n 次，共 n*n 次
    public static void bubbleLike(int[] a) {
        int n = a.length;
        for (int i = 0; i < n; i++) {          // 外层 n 次
            for (int j = 0; j < n; j++) {      // 内层 n 次
                if (a[i] > a[j]) {
                    int t = a[i]; a[i] = a[j]; a[j] = t;
                }
            }
        }
    }
}
```

两层都是 `n`，相乘得 `n²`，复杂度 `O(n²)`。

**例 3：二分缩小 → `O(log n)`**

```java
package com.canoe.dsa;

public class Example3 {
    // 每次区间减半，最多 log2(n) 次
    public static int binarySearch(int[] a, int key) {
        int lo = 0, hi = a.length - 1;
        while (lo <= hi) {
            int mid = (lo + hi) >>> 1;
            if (a[mid] == key) return mid;
            if (a[mid] < key) lo = mid + 1;
            else hi = mid - 1;
        }
        return -1;
    }
}
```

`while` 每轮把区间从 `n` 缩到 `n/2`、`n/4`……直到 1，轮数是 `log2(n)`，复杂度 `O(log n)`。

**例 4：分治递归 → `O(n log n)`**

```java
package com.canoe.dsa;

import java.util.Arrays;

public class Example4 {
    // 归并排序：每层合并共 O(n)，共 log n 层
    public static void mergeSort(int[] a, int lo, int hi) {
        if (lo >= hi) return;
        int mid = (lo + hi) >>> 1;
        mergeSort(a, lo, mid);      // 左半
        mergeSort(a, mid + 1, hi);  // 右半
        merge(a, lo, mid, hi);      // 合并，O(n)
    }

    private static void merge(int[] a, int lo, int mid, int hi) {
        int[] buf = Arrays.copyOfRange(a, lo, hi + 1);
        int i = 0, j = mid - lo + 1, k = lo;
        while (i <= mid - lo && j <= hi - lo) {
            a[k++] = (buf[i] <= buf[j]) ? buf[i++] : buf[j++];
        }
        while (i <= mid - lo) a[k++] = buf[i++];
        while (j <= hi - lo) a[k++] = buf[j++];
    }
}
```

`mergeSort` 把规模 `n` 不断对半分，形成 `log n` 层；每一层的合并操作加起来都是 `O(n)`（因为所有元素在这一层各被处理一次）。层数 `×` 每层工作量 = `O(n log n)`。这正是分治类算法（快排、归并、堆相关操作）的典型复杂度。

**例 5：循环变量翻倍 → `O(log n)`**

```java
package com.canoe.dsa;

public class Example5 {
    // i 每次翻倍: 1,2,4,8,... 约 log2(n) 次
    public static int countPow(int n) {
        int c = 0;
        for (int i = 1; i < n; i *= 2) {
            c++;
        }
        return c;
    }
}
```

`i` 的取值是 `2⁰, 2¹, 2², …`，直到超过 `n`，总共约 `log2(n)` 次，复杂度 `O(log n)`。这是"每次砍半/翻倍"类循环的标志，和二分查找同源。

**例 6：两层不同上界嵌套 → `O(n·m)`**

```java
package com.canoe.dsa;

public class Example6 {
    // 外层 n 次、内层 m 次, 总 O(n*m)
    public static int cross(int n, int m) {
        int c = 0;
        for (int i = 0; i < n; i++) {
            for (int j = 0; j < m; j++) {
                c++;
            }
        }
        return c;
    }
}
```

当 `n` 和 `m` 独立、都随输入增长时，不能简单说成 `O(n²)`，而应是 `O(n·m)`；只有当 `m` 与 `n` 同阶（如 `m = n`）时才退化为 `O(n²)`。这种"多参数分别看"的意识，在分析矩阵、图（顶点数 `V` × 边数 `E`）时尤其重要。

## 八、递归与复杂度

递归是"自己调用自己"，分析它最直观的工具是**递归树**：把每次递归调用画成节点，子调用画成子节点，整棵树的"节点总数"或"每层的代价之和"就是总复杂度。

### 主定理（Master Theorem）一句话结论

对于形如 `T(n) = a·T(n/b) + f(n)` 的递归（把规模 `n` 分成 `a` 个子问题、每个规模 `n/b`、分解合并代价 `f(n)`），主定理给出三种情形：

1. **`f(n)` 比 `n^(log_b a)` 小一截（多项式小）** → 总复杂度 `T(n) = Θ(n^(log_b a))`（被子问题主导）。
2. **`f(n)` 和 `n^(log_b a)` 同量级** → 总复杂度 `T(n) = Θ(n^(log_b a) · log n)`（每层都摊到 `log`）。
3. **`f(n)` 比 `n^(log_b a)` 大一圈（多项式大）且满足条件** → 总复杂度 `T(n) = Θ(f(n))`（被分解合并主导）。

套用前面的例子：归并排序 `T(n) = 2T(n/2) + O(n)`，对应 `a=2,b=2`，`n^(log_2 2)=n`，`f(n)=n` 同量级，落情形 2，得 `O(n log n)`——和我们在第七节手算的一致，主定理只是帮我们"秒答"。

把三种情形各配一个常见递归，下次看到就能直接对号入座：

| 递归式 | a,b | `n^(log_b a)` | `f(n)` | 情形 | 结果 |
| --- | --- | --- | --- | --- | --- |
| `T(n) = 2T(n/2) + O(1)` | 2,2 | `n` | `O(1)` | ① `f` 小很多 | `O(n)`（如建堆自底向上遍历） |
| `T(n) = 2T(n/2) + O(n)` | 2,2 | `n` | `O(n)` | ② 同量级 | `O(n log n)`（归并/快排平均） |
| `T(n) = 2T(n/2) + O(n²)` | 2,2 | `n` | `O(n²)` | ③ `f` 大一圈 | `O(n²)`（分解代价压过子问题） |
| `T(n) = T(n/2) + O(1)` | 1,2 | `n⁰=1` | `O(1)` | ② 同量级 | `O(log n)`（二分查找递归版） |
| `T(n) = 3T(n/2) + O(n)` | 3,2 | `n^1.58` | `O(n)` | ① `f` 小 | `O(n^1.58)`（某些矩阵分块） |

记法小技巧：`n^(log_b a)` 读作"子问题个数 `a` 乘以每个子问题规模 `n/b` 带来的总规模"，它是"子问题那一侧"的代价量级，主定理本质就是拿它和"分解合并那一侧"的 `f(n)` 比大小。

### 斐波那契：从 `O(2ⁿ)` 到 `O(n)`

最经典的"递归反面教材"是朴素斐波那契：

```java
package com.canoe.dsa;

public class FibNaive {
    // 朴素递归：大量重复计算
    public static long fib(int n) {
        if (n < 2) return n;
        return fib(n - 1) + fib(n - 2);  // 同一 fib(k) 被算很多遍
    }
}
```

把递归树画出来，`fib(n)` 展开成 `fib(n-1)` 和 `fib(n-2)`，再各自展开……叶子总数约为 `1.618ⁿ`（黄金比例），也就是说**时间复杂度是指数级 `O(2ⁿ)`**，且空间复杂度是递归深度 `O(n)`。当 `n=50` 时这个朴素写法要算到天荒地老。

**优化一：记忆化（Memoization）**。把算过的 `fib(k)` 存进数组，第二次直接查表：

```java
package com.canoe.dsa;

public class FibMemo {
    // 自顶向下记忆化：每个 fib(k) 只算一次
    public static long fib(int n, long[] memo) {
        if (n < 2) return n;
        if (memo[n] != 0) return memo[n];
        memo[n] = fib(n - 1, memo) + fib(n - 2, memo);
        return memo[n];
    }
}
```

每个 `k` 从 0 到 `n` 只算一次，每次 `O(1)`，时间降到 `O(n)`，空间 `O(n)`（数组+递归栈）。

**优化二：自底向上迭代（DP）**。直接循环，只用两个变量滚动，空间压到 `O(1)`：

```java
package com.canoe.dsa;

public class FibIter {
    // 自底向上：只需前两个值滚动
    public static long fib(int n) {
        if (n < 2) return n;
        long a = 0, b = 1;
        for (int i = 2; i <= n; i++) {
            long c = a + b;
            a = b;
            b = c;
        }
        return b;
    }
}
```

这个例子把"递归思维的坑"和"优化方向"都讲透了：**先识别重复子问题，再用记忆化或迭代把它从指数打回线性**。

## 九、如何衡量与优化

大 O 给了我们从"量级"上比较算法的尺子，但它不是全部。落地时还要记住几条现实经验：

- **常数不可忽略**：当 `n` 不大时，`O(n²)` 里的小常数版本可能比 `O(n log n)` 的大常数版本还快。比如小规模排序，插入排序常数极小，实际常快过归并。这就是很多标准库"快排为主体、小规模切回插入排序"的原因。
- **缓存局部性（Cache Locality）**：数组连续存储，CPU 预取器能一次搬一整块进缓存，访问友好；链表节点散落内存，缓存命中率低，连续遍历反而更慢。这就是为什么"理论上链表插入 `O(1)`"未必真比"数组插入 `O(n)`"快——常数和缓存会翻盘。
- **分支预测（Branch Prediction）**：CPU 会猜你 `if` 走哪边，猜中则流水线不中断。代码里规律性的分支（如顺序遍历）预测命中高；随机分支（如按哈希随机跳）命中低，会拖慢。高性能代码常设法让分支更"可预测"或用无分支写法。
- **渐进之外的硬约束**：大 O 不关心 I/O、网络、锁竞争。一个 `O(1)` 的算法如果每次都跨网络查一次库，照样慢得离谱。**先量（profiling）再优化**，别凭感觉。

把"大 O 说了不算"的几类现实因素汇总成表，便于写代码时随时对照：

| 现实因素 | 大 O 看不到什么 | 什么时候会翻盘 | 应对 |
| --- | --- | --- | --- |
| **常数系数** | 前面的倍数 `2`、`50` | `n` 很小（<几十）时 | 小规模切回简单算法 |
| **缓存局部性** | 是否连续内存 | 数组 vs 链表大量遍历 | 优先连续存储 |
| **分支预测** | `if` 是否规律 | 随机跳转、哈希散列 | 让分支可预测或无分支 |
| **I/O / 网络** | 是否访问外部 | 每次操作都查库/磁盘 | 批处理、加缓存 |
| **锁竞争** | 是否并发 | 高并发共享结构 | 无锁结构、减小临界区 |

最后给一条可执行的方法论：**先想清楚大 O 选对算法骨架 → 再用 profiler（如 Java 的 JFR、VisualVM，C++ 的 perf，Python 的 cProfile）定位真正的热点 → 再针对常数/缓存做局部优化**。算法课教你"选骨架"，工程经验教你"别在错的骨架上抠常数"。这一篇的工具，后续每一章都会反复用到。

## 本篇小结

- **算法 + 数据结构 = 程序**，二者共同决定程序的性能与可维护性。
- 逻辑结构分**集合/线性/树/图**四类；存储结构分**顺序/链式/索引/散列**四类，同一逻辑可多存储实现。
- 算法必须具**有穷/确定/可行/输入/输出** 5 大特性，好算法还追求**正确/可读/健壮/高效**。
- **大 O 表示法**描述增长趋势的上界，只留最高阶、忽略常数系数。
- 常见阶排名为 **`O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ)`**，指数级是灾难。
- 复杂度要分**最好/最坏/平均**三种情况，工程最看重最坏与平均。
- **摊还分析**看"一连串操作的平均单价"，如动态数组扩容均摊 `O(1)`。
- **空间复杂度**算额外空间；**in-place** 指额外空间 `O(1)`；递归深度直接贡献空间 `O(d)`。
- 手算复杂度看**循环层数/每轮次数**；主定理可秒答 `T(n)=aT(n/b)+f(n)` 类递归。
- 朴素斐波那契是 `O(2ⁿ)` 的反面教材，**记忆化/迭代**可优化到 `O(n)`；实际优化还要考虑常数、缓存局部性与分支预测。
